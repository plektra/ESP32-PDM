# Plan T-0077 (2026-11-03): U5 CA-IS3050G TXD/RXD pin fix

One approved item: **T-0076** (CRITICAL, validator 2026-11-03 pdm-4ch, finding C1). The owner answered Q-0052 with **"yes"**.

## Overview

**Package P1 (shared): U5 CA-IS3050G pins 2/3.** The symbol `ESP32-PDM:CA-IS3050G` in `lib/ESP32-PDM.kicad_sym` has
pin 2 = TXD and pin 3 = RXD. That is the CA-IS3052G order. The CA-IS3050G is 2 = RXD, 3 = TXD (CA-IS305x v1.10, p. 5,
Fig. 6-1 / Table 6-1). The cached part facts `docs/part-facts/C528763.md` (T-0074) agree and warn about the 3052G mix-up
(p. 6, Table 6-2). Today `tools/sch_query.py pdm-4ch ref U5` shows U5.2 "TXD" on /IO17 (with R70) and U5.3 "RXD" on
/IO18. As drawn, the ESP32 TX drives the isolator's RXD output and the node cannot use CAN at all.

The fix is a pin-number swap in the symbol only. Pin names, types and positions stay, so no wire moves. Afterwards
/IO17 (ESP32 CAN TX, R70 pull-up) goes to U5.3 TXD and /IO18 (CAN RX) to U5.2 RXD. The pin map in `ARCHITECTURE.md`
(IO17 CAN TX, IO18 CAN RX) is unchanged, R70 stays where it is, and no part, value or cost changes. Because `can` is a
shared sheet and the symbol is in `lib/`, both boards change identically, so the package is `shared`.

Note for the owner: the pdm-hc2 validation of the same day (`2026-11-03-validate-pdm-hc2.md`, line 24) said that
"2 TXD/IO17, 3 RXD/IO18 match". That was wrong. Design-notes §8.5 had the same error and P1 corrects it. The planner
changes no review report.

**Deferred:** none. The fix is a schematic and library edit that needs no mechanical, PCB, prototype, firmware, order
or owner input.

**Decisions:** one row (Q-0052). It corrects the pinout claim in auto decision 61 (the swap to CA-IS3050G). Confirmed
decision 29 is not changed: the CA-IS3050G stays, and its pinout is now right.
